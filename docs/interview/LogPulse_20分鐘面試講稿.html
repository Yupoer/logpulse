LogPulse 技術講稿

正式回答先說清楚架構、請求路徑、故障邊界與證據；白話說明只放在可展開區。

入口頁 差異教學 Evidence index
練習計時20:00

0:00–1:30｜問題與目標

90 秒

「LogPulse 是 log ingestion lab。HTTP API 接收事件後寫入 Kafka，讓同步請求和後續儲存解耦；consumer 將資料寫入 MySQL 與 Elasticsearch，Redis 負責 rate limit 和讀取快取。第一階段先讓本機、Kubernetes 與 AWS lab 可重複驗證，production scope 仍刻意維持最小。」

白話區

先把訊息放到排隊區，API 不必等所有資料庫都完成；但這個比喻不能保證資料永不遺失，仍要看 Kafka、consumer offset 和儲存錯誤處理。

1:30–4:00｜元件與 request flow

150 秒

「每個 LogPulse app instance 同時執行 HTTP server 與 Kafka consumer goroutine。POST `/logs` 經 rate limiter 後由 producer 發到 Kafka；GET `/logs/:id` 先讀 Redis，miss 才讀 MySQL；搜尋由 Elasticsearch 執行；`/metrics` 由 Prometheus scrape，再由 Grafana 顯示。」

Client → LogPulse API → Kafka → consumer → MySQL / Elasticsearch
             └→ Redis (rate limit/cache)
Prometheus → /metrics → Grafana
白話區

像櫃台先收單、廚房照排隊做；Redis 像常用答案的小白板。小白板可能過期，不能取代 MySQL 的資料責任。

4:00–6:00｜API 與資料一致性

120 秒

「既有 `/logs` API 與資料庫 schema 保持不變。Create handler 驗證 JSON、補 timestamp，再呼叫 producer；成功後更新 Redis count。consumer 反序列化後寫 MySQL，再以 batch bulk index Elasticsearch。讀取路徑是 cache-aside，搜尋直接走 Elasticsearch。」

「這是 lab 的明確取捨：MySQL 是事件保存位置，Elasticsearch 是查詢索引；若需要完整重試、死信佇列或跨系統一致性，必須另行設計，不能從目前測試推論出來。」

白話區

索引像圖書館目錄，不是書本本身。目錄壞掉可以重建，但前提是原始資料仍在；這也是目前不能宣稱 zero-loss 的原因。

6:00–8:00｜Graceful shutdown

120 秒

「程式用 `signal.NotifyContext` 接收 SIGINT/SIGTERM。取消 context 後，Kafka `Consume` 結束並關閉 consumer client；`ConsumeClaim` 在 session context 結束時 flush 尚未送出的 batch。HTTP server 使用五秒 shutdown context，等待 in-flight request 與 consumer 完成。」

「Kubernetes pod 額外設定 30 秒 termination grace period，並以 preStop 留出短暫排空時間。這次 AWS lab 已實際送 SIGTERM 並觀察到 shutdown log；這仍不等於 production fault injection 或 zero-loss 保證。」

白話區

像餐廳打烊：不再收新單，把手上的單做完，再關門。若廚房本身壞掉，打烊流程也不能保證餐點完成。

8:00–10:00｜Rate limit 與 observability

120 秒

「Redis Lua token bucket 使用 client IP 作為 key。`/ping` 和 `/metrics` 明確跳過 limiter，避免 health probe 或 scrape 受到流量限制。metrics 使用 route template、HTTP method、status 與固定 Kafka result，避免把 ID 或 request id 放進 label。」

「HTTP metrics 提供 request counter 與 duration summary 的 count/sum；Kafka metrics 記錄 success、ES、MySQL、unmarshal 等結果。這些資料足以做 lab dashboard，但不是完整 distributed tracing。」

白話區

限流像入口的票券機；監控像櫃台統計本日進場人數。不能把每個人的姓名都當統計分類，否則分類數會無限增加。

10:00–12:30｜Compose 與 Kubernetes

150 秒

「Compose 只服務本機開發與 integration dependencies，移除 Nginx；app 直接暴露 `8080`，監控服務是 Prometheus `9090` 與 Grafana `3000`。Kubernetes 使用 `logpulse` namespace，app 是兩副本 ClusterIP Deployment，具有 probes、resource requests/limits、rolling update 和 HPA。」

「lab backend 使用單副本與 `emptyDir`，所以資料不是持久化 production 設計。HPA 需要 Metrics Server；AWS 版本已由 Terraform 建立 add-on，並在 lab 觀察到 metrics 與 HPA。」

白話區

Compose 像同一台電腦上的練習場；Kubernetes 像有排班員的多台工作站。練習場的暫存磁碟不能假裝成正式資料庫備份。

12:30–15:00｜AWS IaC 邊界

150 秒

「Terraform 以 VPC module 建兩個 public subnet 與 Internet Gateway，以 EKS module 建 control plane 和 managed node；預設是單一 `t3.large`，這次因帳號限制用 `t3.small` 兩台完成 lab。另建 immutable ECR、EKS add-ons、GitHub OIDC role、EKS access entry 與 monthly budget。刻意不建 RDS、MSK、ElastiCache、OpenSearch、NAT Gateway、Ingress 或 service mesh。」

「這次已完成 `terraform plan/apply`、kubeconfig、dependencies/app/monitoring/HPA 部署、runtime smoke 與 `terraform destroy`。清理後 EKS、ECR、VPC、Budget 已不存在，KMS key 仍依 AWS pending deletion 流程處理。」

白話區

Terraform 是施工圖，不是已蓋好的房子。沒有帳號就只能檢查圖面，不能宣稱房子真的站得住。

15:00–17:30｜CI/CD 與 immutable image

150 秒

「CI 執行 dependency download、lint、test、vet、build。CD 使用 `workflow_run.head_sha` checkout 已測試 commit，透過 GitHub OIDC 取得 AWS credentials，把 image 以該 SHA 作 immutable tag 推到 ECR，再更新 EKS deployment、等待 rollout status，最後在 cluster 內對 `/ping` 做 smoke test。」

「`EKS_DEPLOY_ENABLED` repository variable 平時保持關閉；本次 lab 驗證時暫時開啟並補齊 variables/secret，完成 OIDC、ECR immutable SHA image、EKS rollout 與 cluster `/ping` smoke test，驗證後立即關閉 gate。這避免把 Docker Hub latest 或未測試的工作樹當成發布版本。」

白話區

SHA tag 像每箱貨都有唯一編號；不能只貼『最新版』，否則出問題時無法知道是哪一箱。

17:30–20:00｜驗證、取捨與收尾

150 秒

「目前已驗證的重點是 Go test、Go vet、metrics middleware、rate-limit probe bypass、Docker Compose、Kubernetes dry-run 與 AWS lab runtime；Prometheus/Grafana scrape、rollout/rollback、shutdown、k6，以及 GitHub Actions CD 的 OIDC、ECR、EKS rollout 和 `/ping` smoke 都有 after evidence。GitHub branch、PR、master CI run `33356543223` 與 CD run `33356650844` 已完成。」

「我會把證據分成 before baseline、after implementation 與 pending runtime。這樣面試時能分清楚『程式已寫』、『本機已測』和『雲端已運行』三種不同命題。」

白話區

考試有寫答案、在家試跑、正式上線三個層級；其中一層通過，不會自動替另外兩層作證。

結尾句：「這個版本已用相同證據索引完成本機、AWS lab 與 GitHub Actions CD runtime 驗證；CD run 完成後已關閉 gate 並清理資源，production SLA 仍不在宣稱範圍。」

正式術語優先；白話區只用於練習理解，不替代技術定義。
