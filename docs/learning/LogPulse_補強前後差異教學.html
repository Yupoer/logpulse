每章先用正確術語，再用生活例子降低理解門檻。生活例子有邊界，不能代替設定、request flow 或證據。

入口頁 20 分鐘面試講稿 Evidence index

1. App instance：HTTP API 與 Kafka consumer

一句話結論：每個 app instance 同時服務 HTTP request 和 Kafka consumer，shutdown 時兩條路徑都要被等待。

日常生活類比

一位店員同時接單和把單送進廚房；打烊時先停止收新單，再把手上的單交接完。

類比限制

店員不是 goroutine，類比沒有描述 consumer group rebalance、offset 或資料庫錯誤；這些仍要看程式與 Kafka 設定。

修改前／修改後

修改前
consumer 在背景啟動，main 沒有等待它結束，也沒有明確關閉 consumer client。
修改後
signal context 取消 consumer、consumer 關閉 client、claim flush batch，main 等待 consumer channel。

真實設定與 request flow

SIGTERM → signal.NotifyContext cancel
  ├─ HTTP Server.Shutdown(5s)
  └─ Kafka Consume(ctx) → ConsumeClaim flush → client.Close()
POST /logs → producer → Kafka → consumer → MySQL + ES

驗證命令

go test ./...
go vet ./...
# runtime（需要 Compose/Kubernetes）
docker compose -f deployments/docker-compose.yml up -d --build
# 另開 terminal 後停止 app，觀察 consumer shutdown log

面試回答骨架

「我用 signal context 做共同取消來源；HTTP server 有 timeout，Kafka claim 在 session context 結束時 flush，main 透過 channel 等 consumer 完成。這證明 shutdown 路徑存在，不等於已做 production fault injection。」

錯誤說法／正確說法

錯誤
「收到 SIGTERM 就立刻 kill，資料一定不會丟。」
正確
「收到 SIGTERM 後停止新工作、flush 目前 batch 並等待；資料可靠度仍受 Kafka、MySQL、ES 和重試策略限制。」

仍不能宣稱什麼

不能宣稱 zero-loss、exactly-once、所有依賴都能在五秒內完成，或已通過 production fault injection。

Evidence path

cmd/api/main.go · internal/repository/kafka_consumer.go · docs/evidence/after/implementation-status.md

2. Metrics 與 rate limiter

一句話結論：用低 cardinality metrics 看 request 與 Kafka 結果，並讓 /ping、/metrics 不受 Redis rate limit 阻擋。

日常生活類比

櫃台統計「哪一種服務、花多久、成功或失敗」，而不是把每位客人的姓名都當成分類；健康檢查和統計人員可直接進門。

類比限制

統計 counter/summary 不會自動告訴你 trace、依賴拓撲或資料內容；Redis token bucket 的一致性仍由 Redis Lua script 提供。

修改前／修改後

修改前
沒有 app metrics；所有路由都先走 rate limiter，probe/scrape 可能收到 429。
修改後
metrics middleware 記錄 route template、status、duration count/sum、Kafka result；/ping 與 /metrics 明確跳過 limiter。

真實設定與 request flow

GET /metrics → Gin metrics middleware → skip Redis limiter → text exposition
POST /logs → metrics middleware → Redis token bucket → handler
labels: method, route template, status, result

驗證命令

go test ./internal/metrics ./internal/middleware
curl http://localhost:8080/metrics
# 確認輸出含 logpulse_http_requests_total 與 duration count/sum

面試回答骨架

「我避免把 user ID、log ID 或 request ID 放進 label，只使用 route template。HTTP duration 先以 summary 的 count/sum 表達，對 lab 足夠；若需要 percentile，可再換成 histogram，但要先確認查詢需求。」

錯誤說法／正確說法

錯誤
「有 metrics 就代表系統可觀測性完整。」
正確
「目前有基本 counter 與 latency summary，能支援 scrape 和 dashboard；尚未包含 trace、structured logs 或完整 SLO。」

仍不能宣稱什麼

不能用本次 lab scrape 推論 production latency，也不能宣稱已完成 trace、structured logs 或完整 SLO。

Evidence path

internal/metrics/metrics.go · internal/metrics/metrics_test.go · internal/middleware/ratelimit.go

3. Compose：移除 Nginx，保留本機邊界

一句話結論：本機 Compose 讓 app 直接暴露 8080，Nginx 不再重複扮演 Kubernetes Service 的角色。

日常生活類比

練習場只有一個入口，客人直接走到櫃台；正式場地才由場館網路規則決定入口和流量。

類比限制

移除 Nginx 不會自動提供 TLS、WAF 或 load balancing；Kubernetes Service、Ingress 或 AWS load balancer 是另一個部署決定。

修改前／修改後

修改前
Compose app 無直接 host port，Nginx 綁定 80 並代理 app。
修改後
Compose app 綁定 \${APP_PORT:-8080}；移除 Nginx service、config 與相關 Makefile 路徑。

真實設定與 request flow

Browser/curl → localhost:8080 → app:8080
Prometheus → app:8080/metrics
app → mysql / redis / kafka / elasticsearch

驗證命令

docker compose -f deployments/docker-compose.yml config
# Docker daemon 可用時：
docker compose -f deployments/docker-compose.yml up -d --build
curl http://localhost:8080/ping

面試回答骨架

「Compose 的目標是 local development 和 integration dependencies，不模擬 production edge proxy。Kubernetes app Service 仍是 ClusterIP；是否加 Ingress 留到 AWS 階段依需求決定。」

錯誤說法／正確說法

錯誤
「沒有 Nginx 就不能做高可用。」
正確
「本機 app 直接暴露 port；高可用由多副本、Service、rolling update 和實際入口層共同決定。」

仍不能宣稱什麼

不能宣稱 local Compose 等同 AWS edge architecture、已提供 TLS，或已驗證多副本流量分配。

Evidence path

deployments/docker-compose.yml · Makefile · docs/evidence/before/nginx.conf（原始 baseline）

4. Kubernetes：namespace、rollout 與 HPA

一句話結論：app manifest 把部署安全邊界寫出來：兩副本、ClusterIP、probes、資源、rolling update、termination grace 和 HPA。

日常生活類比

排班主管先讓新員工上手，再讓舊員工離場；工作量變大時增加班次，變小時慢慢減少班次。

類比限制

Kubernetes 不會替錯誤的 health endpoint、缺失的 Metrics Server 或不可用的 image 修正問題；emptyDir 也不是資料備份。

修改前／修改後

修改前
manifest 混用 default namespace，rollout 與 termination 設定不完整。
修改後
所有 lab 資源進 logpulse namespace；app 設定 maxUnavailable 0、maxSurge 1、30 秒 grace、probes、requests/limits，HPA 設定範圍為 2–6。

真實設定與 request flow

Client → Service logpulse:80 → ready app Pods:8080
HPA → Metrics Server → Deployment replica count
SIGTERM → preStop 5s → app graceful shutdown (30s budget)

驗證命令

kubectl apply --dry-run=client -f k8s/namespace.yaml
kubectl apply --dry-run=client -f k8s/config-secret.yaml
kubectl apply --dry-run=client -f k8s/app.yaml
kubectl apply --dry-run=client -f k8s/hpa.yaml
kubectl -n logpulse rollout status deployment/logpulse-app

面試回答骨架

「我把可觀察的 app lifecycle 寫在 Deployment：readiness 控制進入 Service，liveness 偵測卡住，rolling update 保留可用副本，HPA 設定依 CPU 在 2–6 間調整；本次 runtime evidence 只宣稱 metrics 正常與當下 2 replicas。backend 仍是 lab 的單副本 emptyDir。」

錯誤說法／正確說法

錯誤
「設定 HPA 就一定會自動擴容。」
正確
「HPA 需要 Metrics Server 和可用 resource requests；是否真的擴容要用 cluster runtime 觀察。」

仍不能宣稱什麼

不能宣稱 backend durable、已在壓力下證明 HPA 上限、或 app Service 已對外提供 load balancer；本次 rollback 已有 lab 證據。

Evidence path

k8s/namespace.yaml · k8s/app.yaml · k8s/backends.yaml · k8s/hpa.yaml · k8s/config-secret.yaml

5. Prometheus 與 Grafana

一句話結論：Prometheus scrape app 的 /metrics，Grafana 只用最小 datasource/dashboard，storage 在 lab 以 ephemeral volume 表示。

日常生活類比

Prometheus 像定時抄表員，Grafana 像把抄到的數字畫成圖；抄表頻率和欄位要固定。

類比限制

dashboard 不會創造缺失的 metrics；ephemeral storage 重啟後可能失去歷史資料，不能拿來當長期監控平台。

修改前／修改後

修改前
沒有一致的 scrape target 與可重複的 dashboard provisioning。
修改後
Compose 與 K8s 都有 Prometheus config、Grafana datasource、dashboard，K8s volume 使用 emptyDir。

真實設定與 request flow

Prometheus → http://logpulse:80/metrics → HTTP/Kafka series
Grafana → http://prometheus:9090 → dashboard panels
K8s storage: Prometheus /prometheus = emptyDir; Grafana /var/lib/grafana = emptyDir

驗證命令

docker compose -f deployments/docker-compose.yml config
# cluster 可用時：
kubectl -n logpulse get pods,svc prometheus grafana
curl http://localhost:9090/-/ready

面試回答骨架

「我先把 scrape target 和 dashboard provisioning 固定在版本庫，讓本機與 lab 有相同設定。因為 storage 是 ephemeral，這是驗證用 dashboard，不是保留多年資料的 observability platform。」

錯誤說法／正確說法

錯誤
「有 Grafana 圖表就代表告警和 SLO 都完成。」
正確
「目前有基本 request rate、Kafka result、平均 duration panel；告警規則、長期 storage 和 SLO 尚未建立。」

仍不能宣稱什麼

不能宣稱監控資料已持久化、已建立告警與 SLO，或 lab 結果代表 production observability。

Evidence path

monitoring/prometheus.yml · monitoring/grafana/provisioning/ · k8s/monitoring.yaml

6. Terraform：AWS 施工圖與 lab runtime

一句話結論：Terraform 描述最小 EKS lab 與權限邊界，本次已完成 AWS lab 的 plan、apply、runtime 驗證與 destroy。

日常生活類比

建築圖畫出地基、電線和門禁；圖面完成不代表房子已蓋好，也不代表消防檢查已通過。

類比限制

Terraform module 仍會呼叫 AWS API、產生費用並依賴 provider/module 版本；真正的 plan/apply 需要 credentials 與權限。

修改前／修改後

修改前
沒有可重複的 AWS VPC/EKS/ECR/OIDC/budget 描述。
修改後
新增兩個 public subnets、IGW、ECR immutable、EKS managed node、add-ons、GitHub OIDC role、access entry、budget 與 outputs；設定預設 t3.large，runtime 以 t3.small x2 驗證。

真實設定與 request flow

GitHub Actions OIDC token → IAM role → ECR push + eks:DescribeCluster
Terraform → VPC → EKS → managed node → add-ons
EKS access entry → kubectl namespace/logpulse deploy

驗證命令

terraform fmt -check infra/terraform/aws
terraform -chdir=infra/terraform/aws validate
terraform -chdir=infra/terraform/aws plan
terraform -chdir=infra/terraform/aws apply
terraform -chdir=infra/terraform/aws destroy

面試回答骨架

「我把 lab 範圍限制在 VPC、ECR、EKS、add-ons、OIDC、access entry 和 budget，沒有把 RDS、MSK 或 NAT Gateway 偷塞進來。這次確實完成 AWS lab runtime，但驗證後已 destroy，不能把它說成長期 production 環境。」

錯誤說法／正確說法

錯誤
「Terraform code 在，所以 EKS 已經可用。」
正確
「Terraform code 定義了目標狀態；要等 init、validate、plan、apply 與 kubectl runtime evidence 才能說環境可用。」

仍不能宣稱什麼

不能宣稱資源成本為零、production SLA 已達成，或 OIDC role 已被 GitHub Actions workflow 實際使用；本次 ECR push 是本機 lab 證據。

Evidence path

infra/terraform/aws/ · infra/terraform/aws/README.md · docs/evidence/after/implementation-status.md

7. GitHub Actions：OIDC 與 immutable image

一句話結論：CD 只部署 CI 成功的 workflow_run.head_sha，用 OIDC 推送同一個 SHA image，再 rollout 和 cluster smoke test。

日常生活類比

每箱貨都貼唯一批號，出貨單寫同一個批號；不能只寫「最新一箱」，出事才找不到來源。

類比限制

SHA tag 只能確認版本對應，不能保證 image 內容安全、EKS policy 正確或 smoke test 覆蓋所有功能。

修改前／修改後

修改前
CD 登入 Docker Hub，推 latest 與 github.sha，沒有 OIDC/EKS rollout。
修改後
使用 OIDC、ECR、workflow_run.head_sha、EKS_DEPLOY_ENABLED gate、rollout status 和 cluster /ping smoke test。

真實設定與 request flow

CI success → workflow_run.head_sha
checkout SHA → docker build → ECR:logpulse:<SHA>
aws eks update-kubeconfig → kubectl set image → rollout status
kubectl run curl pod → http://logpulse/ping

驗證命令

git diff -- .github/workflows/ci.yml .github/workflows/cd.yml
# AWS/GitHub 設定完成後才測：
gh workflow run "CI Pipeline"
# 觀察 CD workflow 與 ECR image digest

面試回答骨架

「我讓 CD 使用 workflow run 的 head SHA，而不是 CD 自己 checkout default branch；同一 SHA 會成為 ECR immutable tag。EKS deploy gate 預設關閉，避免 credentials 尚未就緒時誤部署。」

錯誤說法／正確說法

錯誤
「CI 綠燈就代表 production 已部署。」
正確
「CI 是 code gate；CD 還要通過 OIDC、ECR push、EKS rollout 與 cluster smoke test。」

仍不能宣稱什麼

不能宣稱 CD 的 ECR→EKS workflow 已執行；branch、PR 與 CI run 已有證據，ECR image 與 EKS rollout 仍是本機手動 lab 證據，不等於 CD workflow 證據。

Evidence path

.github/workflows/ci.yml · .github/workflows/cd.yml · infra/terraform/aws/main.tf

8. Evidence：把「寫好」和「跑過」分開

一句話結論：before、after、pending 三類證據分開保存，任何未跑過的環境都標記為未 runtime verified。

日常生活類比

食譜、在家試煮、餐廳出餐是三件事；食譜寫得完整，不代表餐廳已通過衛生檢查。

類比限制

證據索引不是測試工具，也不能補造遺失的 log；它只讓讀者知道每個 claim 應該回到哪個檔案或命令。

修改前／修改後

修改前
dirty Kubernetes/設定檔與新改動沒有隔離，README 夾帶過度的 production/benchmark 說法。
修改後
原始狀態保存在 docs/evidence/before/；after index 列出實作、已跑測試、阻塞原因與不可宣稱事項。

真實設定與 request flow

before baseline → implementation diff → local checks
                                      ├→ AWS lab runtime checks (cleaned)
                                      └→ GitHub CD workflow skipped / not runtime verified
claim → evidence path → status (verified / not runtime verified)

驗證命令

git status --short
git diff --check
go test ./...
go vet ./...
git diff -- docs/evidence/before

面試回答骨架

「我先保存 HEAD、dirty diff 和原檔，再把實作證據與 runtime 證據分層。這讓我可以準確說明哪些是程式碼檢查、哪些是本機測試、哪些是已完成的 AWS lab，哪些仍要等 GitHub 權限。」

錯誤說法／正確說法

錯誤
「manifest 存在，所以 EKS 驗證完成。」
正確
「manifest 已實作；沒有 cluster 的 dry-run 或 runtime output 前，狀態是未驗證。」

仍不能宣稱什麼

不能把原本 dirty 檔案算成這次成果，不能把 local lab 當 production，也不能把沒有輸出的命令寫成成功。

Evidence path

docs/evidence/index.md · docs/evidence/before/ · docs/evidence/after/
